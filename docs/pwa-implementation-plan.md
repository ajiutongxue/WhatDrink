## 一、目标和首要原则

将「今天喝点什么茶」做成部署在阿里云 Ubuntu 上、供一个人用的 PWA。保留现有推荐、天气、AI、茶库与库存、知识画像、饮茶记录、新图片上传、统计、设置和数据管理能力。手机以 iPhone Safari 主屏应用为重点，桌面支持 Chrome/Edge。界面沿用现有视觉并适配桌面宽度。

**简单够用是首要原则。** 每增加一个框架、数据表、后台任务或抽象层，都要能指出当前功能确实需要它。优先复用现有算法和数据结构；用少量清晰接口完成单用户应用，不为未来多用户、高并发或长期双端同步预建平台。保留登录保护、导入前安全快照和离线写入可靠性；日常备份由用户手动管理，当前不安排每日自动备份。

已确定的边界：

- 新实现从当前 `master` 开始；旧 `feat/pwa-migration` 本地及远端分支留档，不合并其代码或照搬旧方案。
- 迁移微信小程序的结构化个人数据；旧微信云存储图片不迁移。PWA 中新上传图片仍要正常使用。
- 离线功能的代码范围是浏览已缓存内容、规则推荐、打卡与品饮感受、设置或取消「近期不想喝」；天气、AI、上传图片及其他编辑需要网络。Service Worker 需要 HTTPS 或 localhost 安全上下文，当前公网 HTTP 仅用于在线试用。
- 切换日一次性导入旧数据，此后只在 PWA 写入。小程序源码在验收前保留，切换成功后从工作树移除，Git 历史仍可找回。
- 复用 ECS 已有 Nginx 提供同源 HTTP 静态页面和 API 代理，不使用 Caddy。当前没有配置证书、不跳转 HTTPS；FastAPI/SQLite 保持原实现，API 暂以 `yang` 用户的 `nohup` 后台进程运行。不引入 Docker、Redis、消息队列、ORM 或额外备份服务。
- 当前域名为 `http://tea.xense.com.cn`，项目根目录为 `/home/yang/webapp/tea`，运行数据为 `/home/yang/webapp/tea-data`，公开静态文件为 `/var/www/tea`。操作统一使用 `yang`，需要管理员权限时加 `sudo`，保持现有服务运行。删除文件、修改系统配置、安装软件、重启服务的完整命令须先展示并取得用户确认。
- 用户定期手动将数据库副本复制到其他位置；当前不启用每日备份计时器，也不把 30 天保留作为运维要求。已实现的备份/恢复工具与 systemd 配置保留备用。

## 二、最小实现结构

| 部分 | 决定 | 理由与边界 |
| --- | --- | --- |
| 前端 | `web/`：Vue 3、Vite、TypeScript；先用页面本地状态，页面增多时再按需拆组件或路由 | 保留响应式开发便利；不预建多层状态架构，也不做接口代码生成。 |
| 服务端 | `server/`：FastAPI、Python 内置 `sqlite3`、少量明确的路由 | 负责登录、持久化、天气代理、AI 请求代理和图片。推荐规则继续在浏览器执行。 |
| 数据 | SQLite 中保存一份有版本号的可变应用状态 JSON；另存加密 AI Key、登录会话和已处理的离线请求 ID | 现有 `tea_doctor_v1` 已是一份完整状态；个人数据量小，避免把每个字段拆成大量表。内置知识目录随版本发布；用户另行安装的知识包及其上版备份保存在可变状态中。 |
| 图片 | 文件存服务器目录；记录中保存图片相对路径与说明 | 最多 6 张/条；仅复制数据库不能恢复图片，完整恢复需另存图片目录和服务端环境文件。 |
| 离线 | Service Worker 缓存应用静态文件；IndexedDB 保存最近状态与少量待提交操作 | `/api/*`、认证和第三方请求不进 Service Worker 缓存；当前公网 HTTP 无法注册 Service Worker，离线冷启动留待安全上下文验收。 |
| 部署 | 已有 Nginx 提供同源 HTTP 和静态文件；`yang` 用 `nohup` 启动单进程 Uvicorn | API 只监听 `127.0.0.1:8000`；当前进程没有开机自启或退出后自动重启。systemd 单元已安装但未启用，备份 timer 未启用。 |

`web/`、`server/` 和 `deploy/` 是新代码目录。开发期间保留小程序的 `pages/`、`utils/`、`cloudfunctions/`、`data/` 和 `ui-prototype/`，用作行为与视觉对照。种子茶库和知识画像从当前 JS 数据一次性转换为 PWA 使用的 JSON，确认 89 款茶、86 款完整画像及 3 款预留茶；切换后 JSON 成为 PWA 的唯一内置数据源，避免长期维护两份数据。

### 最小接口约定

- `GET /api/healthz`：不需登录，返回 204、`Cache-Control: no-store`，用于判断服务器是否可达。
- `POST /api/login`、`POST /api/logout`、`GET /api/session`：单用户密码登录；随机会话令牌放在 `HttpOnly; SameSite=Lax` Cookie 中，服务端保存令牌摘要与到期时间。HTTPS 配置使用 `Secure`；当前 HTTP 试用设置 `APP_ENV=development`、`COOKIE_SECURE=false`、`ALLOWED_ORIGIN=http://tea.xense.com.cn`，以满足现有配置校验并允许 HTTP 登录。密码用 `scrypt` 哈希，登录失败做简单限流；写请求核对 `Origin`。HTTP 链路不加密登录密码和会话，但服务端密码哈希、AI Key 加密存储及不返回 Key 明文的规则继续保留。
- `GET /api/state`：返回当前状态和整数 `revision`，不返回 AI Key 明文、密码或会话信息。`PATCH /api/state/{section}` 仅允许 `profile`、`settings`、`teaLibrary`、`inventory`、`knowledgeOverrides`、非密钥 AI 配置；提交 `baseRevision`，版本已变化时返回 409 并让页面刷新后重试。
- `POST /api/knowledge/install`：校验并安装完整基础知识包，只替换基础画像，保留上一版供撤销；恢复上一版使用已有 `PATCH /api/state/knowledgeBase`。个人覆盖、茶库和历史不受影响。
- `POST /api/mutations`：在线写入与离线补交共用，操作仅有 `upsert_history`、`set_avoid`。每项包含客户端生成的 `mutationId`、实体 ID 与完整终态；服务端记录已处理 ID，重复提交返回已处理结果。按提交到服务器的先后顺序覆盖同一实体；这是个人应用对少见多设备并发的明确取舍。
- `POST /api/attachments`、`GET/PATCH/DELETE /api/attachments/{id}`：在线上传、预览、修改说明和软删除新图片；可恢复。校验实际文件类型、大小、记录归属及每条上限，存储时去除图片位置信息；旧 `cloud://` 引用不转换为附件。
- `GET /api/weather`：服务端持有高德 Key 并调用天气接口。`POST /api/ai/chat`：浏览器复用原有 JS 的提示词与结果校验逻辑，服务端只用加密保存的 Key 代理 OpenAI 兼容请求；限制端点为 HTTPS、请求大小与模型参数，拒绝指向本机或内网的地址。
- 设置页在浏览器导出 `tea-pwa-v1` JSON，导出文件不含 AI Key；`POST /api/data/import` 仅接收本应用完整 PWA 导出，`POST /api/data/reset` 重置个人状态，两者在覆盖前创建 SQLite 快照。导入保留现有加密 AI Key，重置则清除它；旧小程序导入的 dry-run、正式迁移和全量备份仍属步骤 6。

所有业务接口要求登录且仅允许同源调用。首页规则推荐、统计与大部分知识展示使用前端已有数据计算，不再为每项计算增加专门的服务端接口。

## 三、按顺序实施

每一步做完再进入下一步。每一步的验收记录写在对应提交或变更说明中；失败时修复本步，不跳到后面的功能。

1. 复核 `git status` 和 `pwa/` 的实际内容；确认旧 `pwa/data/tea.db` 仍只有 89 条种子茶、无个人记录，再精确删除旧未跟踪 `pwa/` 目录。不要动被忽略的 `cloudfunctions/getWeather/config.json`。
2. 保留 `feat/pwa-migration` 分支；从 `master` 建立新工作分支 `codex/pwa-rebuild`。将新运行目录及密钥文件加入 `.gitignore`，让旧虚拟环境不再进入小程序包扫描。
3. 运行 `npm test`、`npm run ui:check`、`npm run verify`，保存基线结果和已知差异。

**验收门槛：** 新分支以 `master` 为基点；旧分支仍可查；旧运行物不在工作树；现有小程序基线检查恢复通过。

### 步骤 2：迁移业务数据与纯逻辑

1. 以 `tea_doctor_v1` 的字段为起点，定义新状态的校验、默认值和版本迁移；AI Key 单独加密保存。`knowledgeBase` 默认来自内置目录，导入的个人知识包及其上版备份可覆盖默认目录。
2. 将推荐、文本解析、茶叶匹配、农历节气、历史排序等与微信 API 无关的 JS 逻辑转为前端可用模块；优先保留函数行为，去掉 `wx.*` 依赖。
3. 实现按 section 保存档案、设置、茶库、库存与知识覆盖；历史和临时回避走同一套 mutation 写入。统计由浏览器基于历史计算。
4. 用固定输入对照小程序现有测试，重点核对硬过滤、推荐排序、自选茶匹配、库存生命周期和历史顺序。

**验收门槛：** 可变数据在刷新和重启后不丢；同一组输入得到与现有小程序一致的关键结果；旧业务测试所覆盖的规则均有可运行的 PWA 对照测试。

**执行记录（2026-09-23）：** 服务端加入 v2 状态校验/迁移、按 section 原子保存、历史与临时回避幂等 mutation、库存生命周期辅助逻辑、知识目录覆盖及上版备份；AI Key 另存密文，状态读取只返回是否已配置。内置知识目录与校验契约一同打包进 `server/seed.json`。浏览器侧复用原有推荐、茶叶匹配、历史排序、农历和知识校验规则；关键字解析去除微信/LLM 依赖，库存与统计逻辑有固定输入对照测试。本地浏览器可正常加载并登录；独立 HTTP 验证档案写入后重启读回，89 款茶和 86 个内置画像仍在。后端 14 项测试、PWA 规则对照测试、前端构建、种子检查和原小程序 `npm run verify` 均通过。页面仍只有步骤 1 的只读预览；业务编辑 UI、离线和安装能力在后续步骤。

### 步骤 3：完成推荐页和在线服务

1. 以原型推荐页为骨架实现日期、农历节气、动态天气背景、状态输入、主推/备选、重新推荐、打卡与品饮文字。
2. 把高德调用移到服务端；定位权限失败时使用档案城市，天气失败时继续规则推荐。
3. 保留现有 AI 解析、深度推荐、每日茶语和新品饮笔记分析的提示词及回退行为；通过服务端代理调用模型。设置页可保存端点、模型、开关和 Key；读取时只显示 Key 是否已配置。
4. 保留取消请求、错误提示和规则回退；AI 失败不能阻止打卡或保存感受。
5. 按 PWA 浏览器页面重新设计布局：页面宽度随可用空间伸缩，内容区只设置最大宽度；高度由内容自然撑开，兼顾浏览器工具栏与安全区，不沿用小程序的固定画布宽高。

**验收门槛：** 固定样例下规则结果与小程序一致；天气、AI 成功与失败路径均可复现；推荐页在窄屏手机、宽屏手机和平板/桌面宽度下自适应，内容高度变化时不截断，主体不超过设定的最大宽度，操作区不被浏览器工具栏或安全区遮挡。测试所用屏幕尺寸只是样本，不作为布局规格。

**执行记录（2026-09-24）：** 推荐页已接上原有规则、农历节气、按时段/天气变化的场景、状态输入、主推/备选、重推、30 天临时回避、打卡和品饮文字。天气由服务端代理高德；定位不可用时可用档案城市，天气失败时规则推荐照常工作。AI 的解析、深度推荐（含可选两阶段）、每日茶语和笔记分析沿用原提示词与本地候选校验，通过同源服务端代理调用；Key 不返回浏览器，取消或失败时保留规则结果。设置页暂只提供本步需要的城市和 AI 配置，其余项目留到步骤 4。浏览器隔离数据验证了规则推荐、打卡、笔记刷新持久化、临时回避和天气失败回退；窄屏无横向溢出，宽屏内容区最多约 1024px。前端构建与规则/AI 测试、服务端 23 项测试、原小程序回归均通过。高德和 AI 的真实凭据在线调用、iPhone Safari 实机仍待后续部署验收；当前成功/失败路径由模拟上游测试验证。

### 步骤 5：安装能力与限定离线使用

## 四、贯穿全程的验收与取舍

- 自动测试只覆盖会造成真实损失或明显行为回退的路径：推荐算法、数据持久化、登录、离线补交、导入回滚和备份恢复。页面视觉用少量代表性屏宽、不同内容高度与人工实机检查；测试尺寸不是布局规格，不堆重复快照测试。
- 每步都保留一个可运行版本，先完成端到端路径，再补齐边缘状态。涉及旧行为不清楚时，以实际小程序代码和 `SPEC.md` 为准，并把必要的行为差异写回文档。
- 当前日常备份由用户手动复制一致性数据库副本到其他位置，周期和保留数量自行决定；服务器本机快照不具备整机损坏后的恢复保障。仅有数据库副本不能恢复上传图片或解密 AI Key；完整恢复需保留图片目录和对应服务端 `.env`。不增加对象存储或额外备份服务。
- “功能迁移完成”与“可正式切换”分开判定。真实 iPhone 安装、离线恢复和实际数据导入未经验证前，不删除小程序源码。

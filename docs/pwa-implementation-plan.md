# 微信小程序迁移到 PWA：分步骤实施方案

> 制定日期：2026-09-23
>
> 状态：步骤 0–1 已完成；步骤 2–8 待实施。本文件是新迁移的执行依据，不代表 PWA 已完成。
>
> 当前基线：`master` 为微信小程序；业务契约以 `SPEC.md` 和现有代码为准，视觉以 `ui-prototype/manifest.json` 及其五页原型为准。

## 一、目标和首要原则

将「今天喝点什么茶」做成部署在阿里云 Ubuntu 上、供一个人用的 PWA。保留现有推荐、天气、AI、茶库与库存、知识画像、饮茶记录、新图片上传、统计、设置和数据管理能力。手机以 iPhone Safari 主屏应用为重点，桌面支持 Chrome/Edge。界面沿用现有视觉并适配桌面宽度。

**简单够用是首要原则。** 每增加一个框架、数据表、后台任务或抽象层，都要能指出当前功能确实需要它。优先复用现有算法和数据结构；用少量清晰接口完成单用户应用，不为未来多用户、高并发或长期双端同步预建平台。必要的登录保护、数据备份和离线写入可靠性不能省掉。

已确定的边界：

- 新实现从当前 `master` 开始；旧 `feat/pwa-migration` 本地及远端分支留档，不合并其代码或照搬旧方案。
- 迁移微信小程序的结构化个人数据；旧微信云存储图片不迁移。PWA 中新上传图片仍要正常使用。
- 离线只保证浏览已缓存内容、规则推荐、打卡与品饮感受、设置或取消「近期不想喝」；天气、AI、上传图片及其他编辑需要网络。
- 切换日一次性导入旧数据，此后只在 PWA 写入。小程序源码在验收前保留，切换成功后从工作树移除，Git 历史仍可找回。
- 服务器原生使用 Caddy、systemd、FastAPI 和 SQLite；不引入 Docker、Redis、消息队列、ORM 或云端备份服务。

## 二、最小实现结构

| 部分 | 决定 | 理由与边界 |
| --- | --- | --- |
| 前端 | `web/`：Vue 3、Vite、TypeScript、Vue Router；用一个简单共享 store 管理当前数据 | 五页状态较多，保留响应式开发便利；不拆多层状态架构，也不做接口代码生成。 |
| 服务端 | `server/`：FastAPI、Python 内置 `sqlite3`、少量明确的路由 | 负责登录、持久化、天气代理、AI 请求代理和图片。推荐规则继续在浏览器执行。 |
| 数据 | SQLite 中保存一份有版本号的可变应用状态 JSON；另存加密 AI Key、登录会话和已处理的离线请求 ID | 现有 `tea_doctor_v1` 已是一份完整状态；个人数据量小，避免把每个字段拆成大量表。内置知识目录随版本发布；用户另行安装的知识包及其上版备份保存在可变状态中。 |
| 图片 | 文件存服务器目录；记录中保存图片相对路径与说明 | 最多 6 张/条；备份数据库时一并备份图片目录。 |
| 离线 | Service Worker 缓存应用静态文件；IndexedDB 保存最近状态与少量待提交操作 | `/api/*`、认证和第三方请求不进 Service Worker 缓存。 |
| 部署 | Caddy 提供同源 HTTPS 和静态文件；systemd 启动单进程 Uvicorn | 一台 Ubuntu 服务器即可维护。 |

`web/`、`server/` 和 `deploy/` 是新代码目录。开发期间保留小程序的 `pages/`、`utils/`、`cloudfunctions/`、`data/` 和 `ui-prototype/`，用作行为与视觉对照。种子茶库和知识画像从当前 JS 数据一次性转换为 PWA 使用的 JSON，确认 89 款茶、86 款完整画像及 3 款预留茶；切换后 JSON 成为 PWA 的唯一内置数据源，避免长期维护两份数据。

### 最小接口约定

- `GET /api/healthz`：不需登录，返回 204、`Cache-Control: no-store`，用于判断服务器是否可达。
- `POST /api/login`、`POST /api/logout`、`GET /api/session`：单用户密码登录；随机会话令牌只放在 `Secure; HttpOnly; SameSite=Lax` Cookie 中，服务端保存令牌摘要与到期时间。密码用 `scrypt` 哈希，登录失败做简单限流；写请求核对 `Origin`。
- `GET /api/state`：返回当前状态和整数 `revision`，不返回 AI Key 明文、密码或会话信息。`PATCH /api/state/{section}` 仅允许 `profile`、`settings`、`teaLibrary`、`inventory`、`knowledgeOverrides`、非密钥 AI 配置；提交 `baseRevision`，版本已变化时返回 409 并让页面刷新后重试。
- `POST /api/knowledge-package`、`POST /api/knowledge-package/rollback`：校验并安装个人知识包，只替换基础画像，保留上一版供撤销；个人覆盖、茶库和历史不受影响。
- `POST /api/mutations`：在线写入与离线补交共用，操作仅有 `upsert_history`、`set_avoid`。每项包含客户端生成的 `mutationId`、实体 ID 与完整终态；服务端记录已处理 ID，重复提交返回已处理结果。按提交到服务器的先后顺序覆盖同一实体；这是个人应用对少见多设备并发的明确取舍。
- `POST /api/attachments`、`DELETE /api/attachments/{id}`：在线上传和删除新图片。校验实际文件类型、大小、记录归属及每条上限，存储时去除图片位置信息；旧 `cloud://` 引用不转换为附件。
- `GET /api/weather`：服务端持有高德 Key 并调用天气接口。`POST /api/ai/chat`：浏览器复用原有 JS 的提示词与结果校验逻辑，服务端只用加密保存的 Key 代理 OpenAI 兼容请求；限制端点为 HTTPS、请求大小与模型参数，拒绝指向本机或内网的地址。
- `GET /api/export`、`POST /api/import?dryRun=1|0`、`POST /api/reset`：设置页可预览并确认 JSON 导入或重置，正式写入前自动备份；服务器命令行导入复用同一校验和写入函数。AI Key 在普通导出中只显示“已配置”，不导出明文；再次导入该占位值时不覆盖已有 Key。

所有业务接口要求登录且仅允许同源调用。首页规则推荐、统计与大部分知识展示使用前端已有数据计算，不再为每项计算增加专门的服务端接口。

## 三、按顺序实施

每一步做完再进入下一步。每一步的验收记录写在对应提交或变更说明中；失败时修复本步，不跳到后面的功能。

### 步骤 0：保全基线并清理旧尝试

1. 复核 `git status` 和 `pwa/` 的实际内容；确认旧 `pwa/data/tea.db` 仍只有 89 条种子茶、无个人记录，再精确删除旧未跟踪 `pwa/` 目录。不要动被忽略的 `cloudfunctions/getWeather/config.json`。
2. 保留 `feat/pwa-migration` 分支；从 `master` 建立新工作分支 `codex/pwa-rebuild`。将新运行目录及密钥文件加入 `.gitignore`，让旧虚拟环境不再进入小程序包扫描。
3. 运行 `npm test`、`npm run ui:check`、`npm run verify`，保存基线结果和已知差异。

**验收门槛：** 新分支以 `master` 为基点；旧分支仍可查；旧运行物不在工作树；现有小程序基线检查恢复通过。

**执行记录（2026-09-23）：** 已在 `codex/pwa-rebuild` 分支；旧 `pwa/` 经数据核对后删除，本地和远端 `feat/pwa-migration` 保留。`.gitignore` 已覆盖未来的构建产物、虚拟环境、运行数据和密钥文件；源文件及种子数据仍可跟踪。`npm test` 通过 7 组测试，`npm run ui:check` 通过 5 页/28 状态/2 视口，`npm run verify` 全部通过；小程序包体积为 1.47 MB（上限 2 MB）。

### 步骤 1：跑通最小前后端链路

1. 初始化 `web/`、`server/`，加入一个 Vue 页面、FastAPI 启动入口、SQLite 初始化和 `/api/healthz`。
2. 从现有茶库及知识目录生成一次性 JSON 种子；首次启动初始化状态，重启不得覆盖后续用户修改。
3. 实现单用户登录、会话 Cookie、`GET /api/state`；页面登录后显示 89 款茶的只读列表。开发环境可用本地环境文件配置密钥，示例文件只放占位值。

**验收门槛：** 本地浏览器可登录、读取种子、退出再登录；重启服务后数据仍在；未登录无法读业务状态，`/api/healthz` 仍返回 204。

**执行记录（2026-09-23）：** `web/` 已提供 Vue 登录及 89 款茶只读列表，`server/` 已提供 FastAPI、SQLite 初始化和会话接口；`server/seed.json` 从现有代码生成，包含 89 款茶、86 个完整知识画像及 3 个暂缺画像。使用临时测试密码在本地浏览器完成登录、退出、再登录；服务重启后刷新仍保留会话与茶库。未登录 `/api/state` 为 401，公开 `/api/healthz` 为 204。后端 6 项测试、前端构建、种子一致性检查及原小程序 `npm run verify` 均通过。当前未实现安装、离线、业务写入或线上部署。

### 步骤 2：迁移业务数据与纯逻辑

1. 以 `tea_doctor_v1` 的字段为起点，定义新状态的校验、默认值和版本迁移；AI Key 单独加密保存。`knowledgeBase` 默认来自内置目录，导入的个人知识包及其上版备份可覆盖默认目录。
2. 将推荐、文本解析、茶叶匹配、农历节气、历史排序等与微信 API 无关的 JS 逻辑转为前端可用模块；优先保留函数行为，去掉 `wx.*` 依赖。
3. 实现按 section 保存档案、设置、茶库、库存与知识覆盖；历史和临时回避走同一套 mutation 写入。统计由浏览器基于历史计算。
4. 用固定输入对照小程序现有测试，重点核对硬过滤、推荐排序、自选茶匹配、库存生命周期和历史顺序。

**验收门槛：** 可变数据在刷新和重启后不丢；同一组输入得到与现有小程序一致的关键结果；旧业务测试所覆盖的规则均有可运行的 PWA 对照测试。

### 步骤 3：完成推荐页和在线服务

1. 以原型推荐页为骨架实现日期、农历节气、动态天气背景、状态输入、主推/备选、重新推荐、打卡与品饮文字。
2. 把高德调用移到服务端；定位权限失败时使用档案城市，天气失败时继续规则推荐。
3. 保留现有 AI 解析、深度推荐、每日茶语和新品饮笔记分析的提示词及回退行为；通过服务端代理调用模型。设置页可保存端点、模型、开关和 Key；读取时只显示 Key 是否已配置。
4. 保留取消请求、错误提示和规则回退；AI 失败不能阻止打卡或保存感受。

**验收门槛：** 固定样例下规则结果与小程序一致；天气、AI 成功与失败路径均可复现；页面在 375×812、390×844 和桌面宽度可操作。

### 步骤 4：补齐其余页面

1. 记录页：时间线、展开、补写/清空感受、临时回避、新图片上传/预览/删除及图片说明。
2. 茶库页：分类筛选、添加/编辑/停用/删除/排序、知识画像及个人覆盖、包装库存全生命周期。
3. 设置页：档案、体质问卷、推荐和 AI 配置、JSON 导出/导入、知识包安装/撤销、重置及简明运行状态；统计页：月度分布、Top 5、近 30 天频率。
4. 共用的弹层、提示和导航提取为组件；样式来自现有原型，再补桌面布局与键盘焦点。

**验收门槛：** `ui-prototype/manifest.json` 的五页、28 个状态逐项可见且关键操作可用；新图片能上传、刷新后预览、删除；茶库/库存/画像修改能持久化。

### 步骤 5：安装能力与限定离线使用

1. 增加 manifest、192/512 及 Apple Touch 图标、Service Worker；只缓存应用壳和静态资源，显示新版本可用提示，用户确认后更新。
2. 用 IndexedDB 保存最近成功拉取的状态和 outbox。断网时立即显示缓存；规则推荐不等待天气或 AI，并显示“离线推荐”。
3. 离线打卡、改感受和改临时回避先写入 IndexedDB，再进入 outbox；联网时按序补交。请求无响应或 401 时保留队列；重新登录后继续提交。队列清空后拉取服务端最新状态。
4. 离线时将图片、茶库/库存/画像编辑、档案设置、AI 和天气入口标记为需要网络。设置页只显示待同步条数、最近同步时间和失败项的重试入口，不做通用冲突管理台。

**验收门槛：** 飞行模式和停止服务器两种情况下均可冷启动、规则推荐和记录；恢复网络后无重复打卡；登录过期不丢 outbox；未提交记录不会被版本更新清掉。

### 步骤 6：一次性迁移与恢复能力

1. 制作读取小程序导出 JSON 的命令行工具。先 `dry-run`：检查结构、茶叶 ID、历史引用、库存与覆盖数据，报告各类数量、异常项和将忽略的旧 `imageFileIDs`，不写库。
2. 正式导入前使用 SQLite backup API 备份旧库；在一个事务中导入 `teaLibrary`、`history`、`temporaryAvoids`、`profile`、`settings`、`llm`、`knowledgeBase`、`knowledgeOverrides`、`inventory`。导入失败回滚并保留原备份；导入完成输出逐类计数与抽样对照。设置页导入复用这套流程。
3. 导入的 AI Key 立即加密保存，原始导出文件由用户自行安全保管，工具不把明文 Key 写入日志。
4. 建立每日服务器本机备份，内容包括 SQLite 一致性快照、上传目录和解密 AI Key 所需的服务端环境文件；只允许服务器管理员读取，保留 30 天，并做一次完整恢复演练。

**验收门槛：** 使用脱敏样本验证 dry-run、成功导入、重复导入保护、失败回滚和备份恢复；真实导入时逐类数量与小程序导出一致，抽样核对记录、库存、覆盖及设置。

### 步骤 7：部署、实机验收和切换

1. 在阿里云 Ubuntu 上以普通服务用户运行 Uvicorn，用 systemd 管理；Caddy 将已有域名配置为 HTTPS，同源提供前端与 `/api`，运行数据存放在发布目录之外。
2. 配置高德 Key、登录密码哈希、AI 加密主密钥和备份目录；部署前备份，执行数据库迁移，部署后检查登录、天气、AI、上传、备份和日志。发布脚本保留上一版本代码，故障时可退回代码并恢复部署前数据库快照。
3. 在 Windows Chrome/Edge 和真实 iPhone Safari 主屏 PWA 完成安装、定位、在线操作、离线冷启动、补交、重新登录、版本升级测试。静态检查或桌面模拟不能代替 iPhone 验收。
4. 确认 PWA 可用后，在小程序停止写入，导出最终 `tea_doctor_v1` JSON，按步骤 6 导入并核对；此后 PWA 成为唯一写入端。保留小程序短期只读核对。

**验收门槛：** 域名证书有效；未登录业务接口拒绝访问；真实数据计数与抽样一致；iPhone 主屏 PWA 和桌面浏览器关键路径通过；最近一次备份可恢复。

### 步骤 8：收尾

1. 更新 `README.md`、`SPEC.md` 和测试命令，以 PWA 的真实行为为准。
2. 在正式切换和观察确认后，从工作树删除小程序专属页面、云函数、微信项目配置及失效测试；保留仍用于 PWA 的内置茶数据、生成脚本和必要文档。
3. 检查 `git status`、构建产物、`.gitignore` 与服务器配置，确认数据库、上传文件、密钥和个人导出文件没有进入 Git。

**验收门槛：** 仓库默认运行方式是 PWA；新环境可按 README 从头启动；历史小程序版本可通过 Git 查找；旧 `feat/pwa-migration` 分支仍留档。

## 四、贯穿全程的验收与取舍

- 自动测试只覆盖会造成真实损失或明显行为回退的路径：推荐算法、数据持久化、登录、离线补交、导入回滚和备份恢复。页面视觉用少量固定视口与人工实机检查，不堆重复快照测试。
- 每步都保留一个可运行版本，先完成端到端路径，再补齐边缘状态。涉及旧行为不清楚时，以实际小程序代码和 `SPEC.md` 为准，并把必要的行为差异写回文档。
- 单机本地备份是用户选定的简化方案；它不能抵御整台服务器或磁盘同时损坏。出现需要跨机器容灾的实际需求时，再增加异地副本。
- “功能迁移完成”与“可正式切换”分开判定。真实 iPhone 安装、离线恢复和实际数据导入未经验证前，不删除小程序源码。

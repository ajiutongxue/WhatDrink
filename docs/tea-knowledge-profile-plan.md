# 茶叶知识画像与批量补全实施方案

> 状态（2026-08-06）：画像详情与个人补录阶段已完成，自动验证通过。现已具备 86 款画像导入、全部合同字段查看与个人覆盖、清空、恢复、锁定、三款空画像的本地补录、脱敏画像发送与双阶段推荐。按记录云同步、库存记录完整生命周期与微信开发者工具/真机验收仍待完成。本文是实施契约，当前运行行为仍以 `SPEC.md` 和现有代码为准。

## 1. 目标

当前茶库有 89 款茶，单款数据主要包含名称、品牌、分类、年份、茶性、咖啡因、季节和自由备注。新需求要让系统不仅了解用户，也能了解每款具体茶，从而在同类茶之间做有依据的比较和个性化推荐。

第一阶段目标：

- 为全部 89 款茶建立结构一致、可比较的基础画像。
- 先由 LLM 根据现有字段生成保守初稿，再由 Codex 制定字段、证据、可信度、输出和校验规范；用户使用其他模型一次或分批补齐数据，校验通过后一次性导入。
- 允许预先指定少量茶款不补齐，用于验证空画像、部分画像和后续补录流程。
- 每个字段区分已确认、外部资料、分类继承、LLM 推测、个人观察、未知和冲突。
- 用户可以随时修改、清空和锁定字段；用户确认后的内容优先级最高。
- 品饮记录持续积累个人感官和身体反应，不覆盖茶叶的客观资料。
- 推荐结果能够说明为什么是这款具体茶，而不只说明为什么是这个茶类。

第一阶段不包含：

- 小程序运行时自动搜索全网。
- 外部关系型数据库、向量数据库或独立服务端。
- 把营销文案、传统茶性或 LLM 推测当作医学和实验事实。
- 未经确认自动覆盖用户手动修改的字段。

## 2. 核心原则

### 2.1 事实、推测和个人体验分层

同一字段必须保留来源和可信度，不能只保存一个看似确定的结果。

```typescript
type KnowledgeStatus =
  | 'confirmed'       // 包装、官方资料或用户确认
  | 'researched'      // 外部资料查证
  | 'inherited'       // 从茶类模板继承
  | 'inferred'        // LLM 或名称推测
  | 'personal'        // 用户实际品饮观察
  | 'conflicted'      // 多个来源互相冲突
  | 'unknown';        // 暂无可靠信息

interface KnowledgeField<T> {
  value: T | null;
  status: KnowledgeStatus;
  sourceType: 'user' | 'package' | 'purchase' | 'official' |
    'retailer' | 'community' | 'category_default' | 'llm' | 'unknown';
  sourceRefs?: string[];       // URL、包装照片 fileID 或文字依据
  evidence?: string;           // 支撑结论的简短摘要，不保存大段网页原文
  confidence: number;          // 0 ~ 1
  updatedAt: number;
}
```

### 2.2 来源优先级

发生冲突时默认采用以下优先级：

1. 用户手动确认并锁定的内容。
2. 用户多次实际品饮记录形成的稳定结论。
3. 包装、说明书和购买凭证。
4. 品牌官网、官方公众号和官方旗舰店。
5. 多个相互独立外部来源的共识。
6. 茶类通用知识。
7. LLM 推测。

外部资料与个人感受可以同时保留。例如官方描述为“花果香”，用户实际只感到焙火香时，两者不互相删除；推荐时个人感受优先。

### 2.3 未知优于编造

- 产品名称没有体现、外部资料也无法确认的字段保持 `unknown`。
- 同名不同年份、不同包装或不同型号不得自动合并。
- 搜索结果不能精确匹配“品牌 + 完整茶名 + 年份/型号”时进入待确认清单。
- 咖啡因、胃部反应、睡眠影响等没有检测或个人证据时，只能标记为类别估计或未知。

## 3. 最终茶叶画像

每款茶按九个方面描述，标准版约 25～35 个核心字段。

### 3.1 基本身份

- 茶名、品牌、系列、年份、茶类。
- 产品型号 `productCode`。
- 包装版本 `packagingVariant`。
- 散茶、饼茶、砖茶、小饼、茶包等形态。
- 产品型号、版本和生产批次；包装净含量属于实体库存。
- 开封和库存属于用户拥有的实体包装，不作为单一茶款的身份字段；同一茶款可以同时存在已开封和未开封库存。

### 3.2 原料与产地

- 产区、细分山场或村寨。
- 茶树品种。
- 原料等级。
- 采摘季节、嫩度和是否拼配。

### 3.3 工艺与陈化

- 发酵/氧化程度。
- 焙火程度。
- 压制方式。
- 仓储信息和陈化年限。
- 青味、火味、堆味等阶段性状态。

### 3.4 香气画像

- 主要和辅助香气标签。
- 香气强度、纯净度和持久度，使用 0～5 级。
- 花香、果香、蜜香、木香、焙火香、陈香等只在有依据时填写。

### 3.5 滋味与汤感

- 甜、鲜、苦、涩，使用 0～5 级。
- 醇厚、顺滑、清爽、回甘、生津和耐泡度。
- 文字标签保留细节，数值用于跨茶款比较。

### 3.6 身体感受

- 刺激度、提神程度。
- 空腹友好度、胃部反应。
- 对睡眠的实际影响。
- 类别推定与个人观察分开保存，个人记录优先。

### 3.7 适饮场景

- 适合的季节、天气和时段。
- 适合独饮、办公、饭后、夜间或慢饮等场景。
- 传统茶性作为经验标签展示，不作为医疗诊断或疗效结论。

### 3.8 冲泡画像

- 器具、投茶量、水温、首泡时间和递增时间。
- 是否润茶、耐泡次数、冲泡难度和容错率。
- 分类参考参数与用户个人最佳参数分开保存。

### 3.9 用户与茶的关系

- 喝过次数、最近饮用日期和当前想喝程度。
- 喜欢程度以及喜欢/不喜欢的具体原因。
- 从多次品饮记录聚合出的个人香气、滋味和身体反应。
- 资料完整度、个人证据数量和结论可信度。

## 4. 数据分层与存储

继续使用 JSON 式结构化数据，但不把所有数据放进一份会整体覆盖的 `teaLibrary` 快照。

```text
版本化基础知识库
    + 用户字段覆盖层
    + 实体包装库存
    + 原始品饮记录
    + 运行时聚合结果
    = 推荐使用的最终画像
```

### 4.1 基础知识库

- 内置 89 款茶的已查证资料、LLM 初稿、来源和可信度。
- 使用版本化 JSON 或可直接 `require` 的等价 JS 数据模块随小程序发布。
- 包含 `schemaVersion` 和 `catalogVersion`。
- 基础知识库更新不直接覆盖用户修改。
- 当前已实现本地落地：`utils/data.js` 的 `knowledgeBase` 以 `profilesByTeaId`、预留 ID、来源生成时间和导入时间保存导入包；`importTeaKnowledgePackage()` 先进行严格校验，再写入本地缓存，并在 `tea_doctor_knowledge_backup_v1` 保留上一版画像。
- `rollbackTeaKnowledgePackage()` 只恢复上一版基础画像，不回退用户资料、历史或可编辑茶库；画像字段会从现有云同步请求中剥离，当前不写入 `tea_doctor`。
- 这不是启动时自动导入：设置页已经提供明确、可见并需用户确认的知识包导入入口；仍不得在 `App.onLaunch` 静默重装数据包。

### 4.2 用户覆盖层

只保存用户修改过的字段，不复制完整画像。

```typescript
interface TeaKnowledgeOverride {
  teaId: number;
  patch: Record<string, unknown>;
  lockedPaths: string[];       // 例如 knowledge.sensory.aromaTags
  updatedAt: number;
}
```

- 用户修改具有最高优先级。
- `lockedPaths` 中的字段不能被后续目录升级或联网资料覆盖。
- 删除/清空字段也需要 tombstone，避免云端旧值复活。

### 4.3 实体包装库存

茶叶画像描述“这款茶是什么”，库存描述“用户实际拥有多少个包装以及各自状态”。一款茶与库存记录是一对多关系。

```typescript
interface TeaInventoryItem {
  id: string;                  // 稳定库存记录 ID
  teaId: number;
  packageType: 'sample' | 'retail' | 'split' | 'gift' | 'custom' | 'unknown';
  packageLabel?: string;       // 例如“5g试饮装”“50g正装”
  sku?: string;                // 商家商品编号
  purchaseUrl?: string;        // 实际包装对应的商品页
  status: 'sealed' | 'opened' | 'finished';
  quantity: number;            // 未开封同规格包装可合并计数；已开封通常为 1
  unitType?: 'cake' | 'tin' | 'box' | 'bag' | 'sachet' | 'other';
  netWeightPerUnit?: number;   // 克，可空
  remainingWeight?: number;    // 已开封包装剩余克数，可空
  remainingSessions?: number;  // 不称重时估算剩余泡数，可空
  batchLabel?: string;
  openedAt?: number;
  note?: string;
  updatedAt: number;
  deletedAt?: number;          // 删除 tombstone
}
```

- 同一 `teaId` 可以同时关联多条 `sealed` 和 `opened` 记录。
- 相同规格的未开封包装可以用 `quantity` 合并记录，避免逐盒录入。
- 从未开封库存中开一份时，减少原记录数量并创建独立的已开封记录，以便记录开封时间和剩余量。
- “已开封”和“未开封”不能互相覆盖；列表汇总示例为“已开 1 · 未开 3”。
- 基础知识数据包的一次性导入不得创建、修改或删除用户库存。

### 4.4 原始品饮记录

- 继续使用 `HistoryEntry` 保存每次品饮的文字、图片、时间和冲泡信息。
- 单次感受不直接改写茶叶客观画像。
- 聚合结果可以重新计算，原始记录必须保留。

### 4.5 云同步目标

- 基础知识库随版本发布，不重复写入每个用户的云端文档。
- 用户覆盖按茶款/字段的 `updatedAt` 合并。
- 库存按稳定库存记录 ID 和 `updatedAt` 合并；删除使用 tombstone，避免旧设备恢复已删除包装。
- 品饮历史仍按稳定事件 ID 合并。
- 画像上线前必须从当前“整库最后写入胜出”迁移，避免一款茶的修改覆盖整库其他变化。
- 导入导出需要包含基础目录版本、用户覆盖和锁定状态。

## 5. 批量生成与查证流程

### 5.1 LLM 初稿

- 输入现有茶名、品牌、分类、年份、型号和备注。
- 名称中明确出现的“足火”“寿眉”“饼茶”等可给较高置信度。
- 香气、滋味和身体感受等名称未提供的信息只能低置信度推测。
- 所有 LLM 生成字段标记为 `inferred`，不能伪装成已查证事实。

### 5.2 规则与数据包规范

初稿完成后，由 Codex 产出并冻结以下规范，再开始全量数据生产：

- 字段字典、数据类型、枚举值、必填/可空规则和数值量表。
- 来源优先级、可信度计算、冲突保留和未知字段表达方式。
- 可直接交给其他模型使用的统一提示词、输入模板和输出 JSON 示例。
- 分批任务的切分规则、稳定 `teaId` 映射、批次合并和重复记录处理规则。
- 自动校验脚本和人工审核清单。
- 最终导入包的版本、清单、校验结果和回滚信息。

初稿用于暴露字段问题和校正规范；规范冻结后，正式数据必须按统一格式重新输出或转换，不能直接混入结构不一致的早期草稿。

第一版机器可读资产已经建立：

- `data/tea-knowledge.contract.json`：35 个茶叶画像字段以及实体包装库存字段的唯一契约；当前结构版本为 v2。
- `docs/tea-knowledge-field-guide.md`：面向人工审核的中文字段说明，解释状态、来源、量表和容易混淆的字段。
- `utils/teaKnowledge.js`：对目录版本、89 个稳定 ID、预留清单、字段结构、来源、证据、可信度和数值范围执行完整校验。
- `data/tea-knowledge.samples.json`：三款样板的保守初稿；未知字段显式保存为 `null + unknown + 0`，不以猜测填满。
- `scripts/generate-tea-knowledge-contract.js` 与 `scripts/generate-tea-knowledge-samples.js`：可重复生成上述 JSON，避免手工编辑造成结构漂移。
- `tests/tea-knowledge.test.js`：覆盖有效样板、错误量表、错误来源、缺字段、重复 ID、总数不符和预留茶款等拒绝规则。
- `docs/tea-knowledge-batch-rules.md`：可直接交给其他联网模型的任务指令、来源优先级、可信度范围、产品匹配和人工抽查规则。
- `data/tea-knowledge.batch-input.json`：按稳定 ID 生成的 5 个研究批次，当前 86 款待补全、3 款预留测试。
- `scripts/generate-tea-knowledge-batch-input.js`：允许调整预留 ID 和批次大小并重新生成输入包。
- `scripts/validate-tea-knowledge-catalog.js`：分别以批次模式和最终完整导入模式校验其他模型的输出。
- `data/tea-knowledge-research-batches/`：五个可直接交给其他模型的独立输入文件及 manifest。
- `scripts/merge-tea-knowledge-batches.js`：在全部批次通过校验后合并最终导入包；重复、缺失或预留清单不一致时拒绝写入。
- `scripts/migrate-tea-knowledge-v1-to-v2.js`：把早期画像中的单一净含量移出茶叶身份，并按35字段重新计算完整度。
- `docs/tea-knowledge-missing-links-batch-01.md`：第一批无法唯一匹配的商品清单，供用户补充实际购买链接和包装信息。

这些资产已经可以通过设置页的本地受控导入入口安装为基础知识库，并已接入画像编辑和双阶段推荐；基础画像、个人覆盖与库存仍未接入按记录云同步。

### 5.3 使用其他模型批量补全

- 以“品牌 + 完整茶名 + 年份 + 产品型号”为基本检索式。
- 优先使用包装、购买记录和官方来源。
- 只保存结构化结论、短证据和来源链接，不复制长篇营销内容。
- 同名不同批次分别处理；匹配不唯一时不自动采用。
- 用户可以使用一个或多个其他模型一次完成，也可以按茶类或批次分多次完成。
- 不同模型必须遵守同一字段和证据规范；模型名称只记录在批次元数据中，不影响运行时数据结构。
- 分批结果按稳定 `teaId` 合并；同一字段冲突时保留冲突和来源，不按最后文件静默覆盖。
- 联网补全是发布前的数据生产任务，第一版不在小程序运行时发起网页搜索。

### 5.4 测试预留茶款

- 批量任务开始前确定 `withheldTeaIds`，建议预留 3～5 款且覆盖不同茶类。
- 预留茶款仍保留当前基础身份，但知识画像为空或仅有分类继承字段。
- 预留必须列入 manifest 的 `withheldTeaIds`；正式数据包可以不包含这些 ID 的知识画像，从而与搜索失败、模型遗漏和真实未知区分。
- 推荐、茶库详情、完整度、编辑、后续补录和同步都必须能正常处理预留茶款。
- 预留清单属于导入包 manifest，不应写死在推荐算法中；测试结束后可用增量数据补齐。

### 5.5 一次性导入

最终导入包至少包含：

```typescript
interface TeaKnowledgeImportManifest {
  schemaVersion: number;
  catalogVersion: string;
  generatedAt: number;
  batches: Array<{ batchId: string; model?: string; teaIds: number[] }>;
  withheldTeaIds: number[];
  expectedTeaCount: number;    // 当前为 89
}
```

- 导入前校验 JSON 语法、schema 版本、89 个稳定 ID、重复 ID、枚举、取值范围、来源、可信度和预留清单。
- 非预留茶款缺失、同一 ID 重复、未知字段混入或结构版本不兼容时拒绝导入并给出完整错误清单。
- 导入必须先生成当前数据备份，再以原子方式一次写入；不得出现只导入一部分的中间状态。
- 导入基础知识库时不覆盖用户覆盖层、锁定字段和历史记录。
- 导入成功后记录 `catalogVersion`、校验摘要和导入时间，便于回滚和复现。

当前实现状态（2026-08-05）：`importTeaKnowledgePackage()` 已完成严格校验、单次本地写入、上一版画像备份、版本/时间记录、机器可读校验摘要和失败恢复；设置页会识别 `purpose: import` 的文件并在明确确认后安装。`tests/tea-knowledge-storage.test.js` 覆盖成功导入、无效包拒绝、写入失败、回滚、覆盖与库存，以及云同步剥离。仍不在启动时自动执行导入。

### 5.6 用户审核

- 画像详情展示来源、可信度、冲突和待确认项。
- 用户可以修改、锁定或清空任何字段。
- 用户确认后形成覆盖层，不直接改写基础目录。

### 5.7 持续学习

- 打卡后每次最多追问一两个轻量问题，避免增加记录负担。
- 可轮换询问最明显的香气、甜苦涩、浓淡、胃部反应或睡眠影响。
- 自由笔记由 LLM 保守提取结构化感官和明确态度；低置信度观察保持未知。

## 7. 茶库界面需求

### 7.1 列表页

- 保留当前茶名、品牌、年份、茶性和咖啡因信息。
- 增加少量核心风味标签和画像完整度。
- 库存以聚合摘要显示，例如“已开 1 · 未开 3”，两种状态可以同时出现。
- 不在列表中展开全部 25～35 个字段。

### 7.2 画像详情/编辑

按以下折叠区展示：

1. 基本资料。
2. 原料与工艺。
3. 风味画像。
4. 冲泡方式。
5. 个人感受。
6. 库存包装。
7. 资料来源和冲突。

每个字段支持查看来源和可信度；用户可编辑、清空和锁定。未知字段明确显示“待补充”，不显示推测性占位文案。

### 7.3 当前实现状态（2026-08-06）

- 茶库画像弹层已按合同分区展示全部 35 个字段的有效值、状态、来源、可信度、证据和来源引用。
- 每个字段可独立建立个人覆盖；非必填字段可清空，已有覆盖可恢复基础值，并可设置字段锁定。
- 无基础画像的预留茶款和用户新增茶款可直接建立合同校验通过的个人补录，不会自动生成或改写基础画像。
- 茶库列表会区分画像完整度、个人补录数量和多包装库存摘要；第二阶段推荐会读取脱敏后的结构化个人补录。
- 自动测试覆盖空画像补录、字段锁定、非法值拒绝和必填字段清空拒绝；微信开发者工具与真机的弹层滚动、键盘和交互仍需手动验收。

## 8. 推荐接入要求

采用“本地硬过滤 + LLM 粗选 + 本地多样化保险 + LLM 精选”的双阶段混合流程。双阶段先作为可切换实验能力，与当前单阶段推荐对比验证后再决定是否默认启用。

### 8.1 候选边界

- 当前硬过滤规则保持统一，规则推荐和两次 LLM 调用共享同一份 `eligibleTeas`。
- 第一轮接收当次全部合格候选，而不是固定传入 89 款全库；被停用、今天已喝、临时回避、达到连续上限或明确回避的茶不得进入第一轮。
- 不得恢复按数组顺序取前 20 款等静默截断。
- 两轮返回值都使用稳定 `teaId`，并分别校验是否属于该轮候选边界。

### 8.2 第一轮：高召回粗选

- 第一轮使用现有推荐模型，不新增第三个模型配置。
- 每款候选只传稳定 ID、名称、分类、年份/型号、茶性、刺激度、3～5 个核心风味、个人偏好信号、最近饮用和库存摘要。
- 不传长篇产品介绍、完整来源、证据原文和详细冲泡说明。
- 模型返回候选 ID、粗略适配分、选择维度和建议分组，不直接产生最终推荐。
- 建议分为“当前适配”“个人偏好”“值得探索”三组，避免一个排序目标吞掉其他有价值候选。

### 8.3 本地多样化与保险候选

第一轮 LLM 的输出不能直接成为第二轮候选池。本地代码需要合并并重排：

```text
第二轮候选池 = 第一轮 LLM 粗选
             ∪ 本地规则高分候选
             ∪ 用户明确偏好中的强候选
             ∪ 适配范围内的探索候选
```

- 第二轮目标候选数为 12～18，具体数量按合格候选数和上下文预算调整。
- 没有明确茶类偏好时，单一茶类默认不超过第二轮候选池的 40%；在适配分差距合理且有足够候选时，至少覆盖 3 个茶类。
- 普通“想喝岩茶”视为软偏好，可以提高岩茶占比但仍保留相邻选择；“只喝/就想喝岩茶”视为强限定，允许放宽到全部或绝大多数岩茶。
- 多样化只从仍然适合当前状态的候选中选择，不能为了凑茶类数量塞入明显不合适的茶。
- 当硬过滤后可用茶类不足、用户有强限定或某一茶类显著领先时，类别上限自动放宽。
- 如果第一轮返回的 20 款全部是岩茶，而用户没有强限定，本地层必须按以上规则重建候选池，不能原样进入第二轮。
- 40% 和 12～18 都是初始实验参数，应由场景测试调整，不作为永久硬编码常量。

### 8.4 第二轮：完整画像精选

- 第二轮只接收多样化后的候选池，并传入完整结构化画像、个人品饮结论、冲泡经验和当日上下文。
- 第二轮选择主推和备选；主推以当前适配和个人偏好为主，备选在仍适合的前提下提供相邻口味或探索价值。
- 用户实际品饮结论优先于官网营销描述，已锁定字段优先于所有自动信息。
- 推荐理由必须引用实际参与判断的具体属性，并区分客观资料、个人记录和传统经验。

### 8.5 库存、降级与验证

- 推荐链路读取库存时必须按多包装聚合；存在已开封库存不代表该茶没有未开封库存，反之亦然。
- 第一版不因已开封/未开封自动改变推荐分数；是否优先消耗已开封茶作为后续可配置策略。
- 第一轮失败时可由本地规则构造第二轮候选；第二轮失败时回退到本地规则推荐。推荐成功后的“重新推荐”会在下一轮共享候选边界中临时排除上一轮主推和备选，只生效一次，不写入历史或长期回避。
- 保留单阶段模式作为对照，记录两种模式的用户选择、候选遗漏率、稳定性、硬过滤违规、延迟、Token 成本和回退率。
- 在盲测没有证明双阶段明显改善推荐质量前，不将其设为不可关闭的唯一流程。

### 8.6 当前实现状态（2026-08-05）

- 已加入默认关闭的 `twoStageRecommendationEnabled` 实验开关，关闭时保留原单阶段推荐。
- 第一轮接收本地硬过滤后的全部 `eligibleTeas` 摘要，返回值以稳定 `teaId` 校验；越界、重复或无效 ID 不进入下一轮。
- 本地候选池合并第一轮结果、规则高分候选和其余合格保险候选；候选充足时取 18 款，少于 12 款时保留全部，同类默认不超过 40%。检测到“只喝/就想喝”类强偏好时放宽类别上限。
- 第二轮只接收重建后的候选池，附带去除来源链接、证据原文、购买链接、原始品饮笔记和图片后的结构化画像、字段覆盖、锁定路径、最近结构化个人品饮结论及多包装库存摘要。
- 最终主推和备选优先按 `teaId` 绑定，茶名仅用于兼容旧模型返回；两轮都不能选择本轮候选池之外的茶。
- 第一轮失败时仍由本地规则构造第二轮池；第二轮失败时回退本地规则推荐。库存开封状态不参与自动加分。
- Node 语法检查、请求合同测试、候选池多样性测试和 `npm run verify` 已纳入验证；微信开发者工具与真机的真实双请求仍需手动验收。
## 9. 迁移与防回退

实施时必须包含：

- 为基础知识库增加 `schemaVersion` 和 `catalogVersion`。
- 按稳定 `teaId` 建立迁移，不能只按可能变化的显示名称匹配。
- 修正 `id: 14` 为寿眉马饼；不得把“白牡丹”从旧云端快照重新带回。
- 为 `id: 35` 写入 `AT102`，为 `id: 34` 写入 `AT102A`。
- 旧用户的自定义名称和已锁定字段不得被自动迁移覆盖。
- 新增字段需要贯通默认构造、保存、导入、导出、云合并和重置流程，不能被旧字段白名单静默丢弃。
- 旧的茶款级 `disabled` 或单一库存状态迁移时不得臆造包装数量；无法还原时创建待用户确认的库存摘要。

## 10. 实施顺序

1. 完成三款样板初稿，用于发现字段和证据问题，不写入正式茶库。
2. 由 Codex 固定字段字典、枚举、来源、可信度、提示词、输出和校验规范。
3. 用户确定 `withheldTeaIds`，使用其他模型一次或分批补齐其余茶款。
4. 合并批次、执行自动校验并形成人工待确认清单。
5. 实现基础目录、一次性导入、用户覆盖、迁移和云同步。
6. 备份现有数据并一次导入通过校验的最终数据包。
7. 实现画像详情和编辑界面。
8. 让规则推荐和 AI 推荐读取紧凑画像。
9. 用预留茶款验证空画像、部分画像和后续补录流程。
10. 完成自动测试、微信开发者工具和真机验证后发布。

## 11. 验收标准

- 89 款茶全部有基础画像，未知字段明确可见。
- 三款样板的身份、型号和原料等级不再混淆。
- 每个非用户字段能够说明来源、证据摘要和可信度。
- LLM 推测不会显示为已查证事实。
- 分批使用不同模型生成的数据可以通过同一规范合并和校验。
- 预留茶款与真实缺失数据能够明确区分，空画像状态不影响推荐和编辑流程。
- 一次性导入失败时不产生部分写入，成功后可以追溯版本并回滚。
- 用户修改在重启、同步、导入导出和基础目录升级后仍然保留。
- 同一茶款的已开封和未开封库存可同时保存、展示和同步，修改其中一条不会覆盖其他包装。
- 两台设备修改不同茶款时不会因整库覆盖互相丢失。
- 全部合格候选仍参与推荐，模型返回值仍受候选边界校验。
- 推荐能给出产品级理由，并优先采用用户实际体验。
- `npm run verify`、微信开发者工具编译和真机关键流程验证通过。

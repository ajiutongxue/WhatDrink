# 茶叶知识批量补全规则

本规则用于把 `tea-knowledge.batch-input.json` 中的一批茶交给具有联网能力的模型处理。每次任务同时提供以下三个文件：

1. `data/tea-knowledge.contract.json`
2. `data/tea-knowledge.samples.json`
3. 输入包中当前批次的 `batchId`、`teaIds` 和 `teas`

字段中文含义见 `docs/tea-knowledge-field-guide.md`。

当前生成的输入包暂时预留以下三款，分别覆盖绿茶、凤凰单丛和普洱熟茶：

- `id: 0` 禹蒙蒙顶雪芽。
- `id: 25` 宋凰蜜韵蜜兰香。
- `id: 68` 大益 7572 小饼茶。

这是可调整的测试清单，不会写死进推荐算法。重新生成输入包时可使用 `--withheld` 指定其他 ID；使用 `--withheld none` 表示不预留。正式交给其他模型之前应最终确认一次清单。

## 1. 可直接交给其他模型的任务指令

你正在为个人茶库制作产品级茶叶知识画像。请逐款联网检索本批次的茶，严格按照提供的 contract 和 sample 输出一个 JSON 文件。

目标是准确、可追溯和可比较，不是尽量填满。没有可靠证据时必须使用 `unknown`；不得根据茶类常识伪造具体产品事实。

必须遵守：

- 以 `teaId` 为唯一主键，不改变 ID，不新增输入之外的茶。
- 先确认品牌、完整产品名、年份、型号和包装是否对应，再采用网页内容。
- 同名不同年份、规格、包装或型号必须分别处理。
- 输入中的 `confirmedClarifications` 是用户已确认事实，优先级最高，不得被网页覆盖。
- AT102 与 AT102A 是不同产品，任何资料都不得串用。
- 品品香马饼的原料等级是寿眉，不是白牡丹。
- 搜索摘要只能用于发现网页，不能单独作为最终证据；尽量打开原页面核对。
- 用户提供的具体商品页若无法读取，只有包含同一商品 ID 的页面、订单或实物截图才能用于确认；不得用名称相似但商品 ID 不同的搜索结果解释该链接。
- 每个 `researched` 字段必须包含来源链接和简短证据。
- LLM 根据名称做出的判断使用 `inferred`，来源必须是 `llm`。
- 茶类通用知识使用 `inherited`，来源必须是 `category_default`。
- 香气、滋味、身体影响和耐泡度若缺少该产品证据，不得仅凭茶类印象给高置信度数值。
- 不复制大段营销文字，只保存短证据、结构化结论和来源链接。
- 输出只能是合法 JSON，不加 Markdown 代码围栏，不附加正文说明。

输出目录要求：

- `schemaVersion` 与 contract 一致。
- `purpose` 使用 `import`。
- `catalogVersion` 使用能够识别当前批次的唯一版本名。
- `expectedTeaCount` 始终填写完整茶库数量 89，不是本批数量。
- `withheldTeaIds` 原样复制输入包清单。
- `batches` 只记录本次批次，包含当前 `batchId`、实际模型名称和全部本批 `teaIds`。
- `teas` 只输出本批次画像，每款 `lifecycle` 使用 `complete`。
- 35 个茶叶画像字段都必须存在；可以未知，但不能删除字段。
- 包装克数、试饮装或正装、SKU 和购买链接属于库存包装，不写入茶叶画像。

## 2. 来源优先级

由高到低采用以下顺序：

1. 用户确认信息。
2. 实物包装、标签和购买记录。
3. 品牌、生产商或官方旗舰店的具体商品页面。
4. 能够明确对应年份、型号和规格的可靠零售页面。
5. 多个相互印证的专业资料或测评。
6. 单一社区内容。
7. 茶类通用知识。
8. LLM 推测。

低优先级来源不得静默覆盖高优先级来源。两个可靠来源发生冲突时，使用 `conflicted`，把冲突摘要写入 `research.conflicts`，不要任选一个伪装成确定事实。

不接受以下来源方式：

- 只凭搜索结果标题或摘要作结论。
- 无法确认对应具体产品的同品牌相似茶。
- 聚合采集站、内容农场或没有原始出处的转载。
- 用其他年份、包装、净含量或型号的资料替代当前产品。
- 用品牌营销形容词直接转换成精确的 0～5 数值。

## 3. 可信度建议

可信度描述的是证据可靠程度，不是茶叶品质。

| 范围 | 使用条件 |
|---|---|
| `1` | 用户明确确认，或实物包装内容无歧义 |
| `0.90～0.99` | 官方具体产品资料，且年份、型号、规格匹配 |
| `0.75～0.89` | 可靠零售资料或多个来源相互印证 |
| `0.55～0.74` | 单一间接来源，或茶类默认知识 |
| `0.30～0.54` | 有合理依据但仍需核实的模型推测 |
| `0` | `unknown` |

如果来源可靠但产品匹配不完全，应降低可信度并在 `evidence` 说明差异；匹配风险较大时直接保留未知。

## 4. 产品匹配检查

采用某个网页前至少比较：

- 品牌或生产商。
- 完整产品名称。
- 产品型号或货号。
- 年份或批次。
- 包装版本。
- 净含量和形态。
- 茶类、原料等级与产区。

名称相似不代表同一产品。无法唯一匹配时，将候选来源和疑点写入 `research.notes`，相关字段保持未知。

## 5. 数值与标签规则

- 香气、滋味和体感量表均为 0～5，可使用一位小数。
- 苦味和涩味数值越高表示强度越高，不表示越差。
- `emptyStomachFriendliness` 越高表示相对越友好。
- `sleepImpact` 越高表示潜在影响越大。
- 标签应使用简短、可比较的中文词，避免完整营销句子。
- 同义词尽量统一，例如焙火香与烘焙香不要在同一画像重复表达。
- 水温和秒数必须输出范围对象；只有单一建议时，最小值和最大值可以相同。
- 分类默认值只能标记为 `inherited`，不能伪装成该产品的联网查证结果。

## 6. 完整度与未知值

`research.completeness` 等于 35 个茶叶画像字段中 `value` 非空的比例，保留四位小数。它只表示填写比例，不表示真实性和质量。

以下情况应使用未知：

- 没找到资料。
- 资料无法唯一对应当前产品。
- 不同来源冲突且不能判断。
- 只能靠品牌或茶类印象猜测产品风味。
- 医学或身体影响缺少可靠依据。

未知字段固定使用：`value` 为 `null`、`status` 为 `unknown`、`sourceType` 为 `unknown`、`confidence` 为 `0`。

## 7. 分批操作流程

1. 从输入包复制一个完整批次，不要自行拆散或跨批重复。
2. 把本规则、contract、sample 和当前批次一起交给模型。
3. 保存模型返回的原始 JSON，不要先手工修饰。
4. 对每个批次运行校验：

   `node scripts/validate-tea-knowledge-catalog.js path-to-batch.json`

5. 把完整错误清单交回模型修正，直到批次校验通过。
6. 人工抽查产品匹配、来源页面和高置信度字段。
7. 所有批次完成后再合并；禁止边生成边写入小程序正式茶库。
8. 合并后的最终文件使用严格完整模式校验：

   `node scripts/validate-tea-knowledge-catalog.js path-to-import.json --import`

生成或重新切分输入包的命令：

`node scripts/generate-tea-knowledge-batch-input.js --withheld 0,25,68 --batch-size 20`

生成后，五个可以直接上传的批次文件位于 `data/tea-knowledge-research-batches`。每次向其他模型提供四个文件：本规则、contract、sample，以及一个 `research-XX.input.json`。从 `research-01` 开始，模型返回结果建议保存为对应的 `research-XX.output.json`。

五批全部校验通过后，使用以下方式合并；实际命令中依次列出五个输出文件：

`node scripts/merge-tea-knowledge-batches.js batch1.json batch2.json batch3.json batch4.json batch5.json --out data/tea-knowledge.import-v1.json --catalog-version research-v1`

合并器会再次检查全部 89 个 ID、三款预留、批次重复、画像重复和字段契约。任何错误都会在写入最终文件之前停止；已存在的输出文件也不会被覆盖。

## 8. 人工抽查清单

每批至少抽查以下内容：

- 所有 `confidence` 大于等于 0.9 的字段。
- 所有具体型号、年份、净含量、产区和原料等级。
- AT102、AT102A 以及其他同名近似产品。
- 所有身体影响字段。
- 只引用一个非官方来源的字段。
- `research.conflicts` 与 `research.notes` 中列出的风险。

出现明显串款、伪造链接或把推测标成查证事实时，应整批退回修正，而不是只修一个字段后继续导入。
